Лабораторная работа №14 (УСРС)
Оптимизация запросов учебной базы данных

Цель

Оценить производительность запросов к БД учёта студентов, занятий и оценок.
Найти дорогие операции, проверить изменения на тестовой копии и сравнить результаты.

1. Состояние исходной базы

PostgreSQL 18.6 (Postgres.app), macOS, Apple Silicon. В рабочей базе 20 таблиц,
79 студентов и 1 077 оценок. По pg_stat_user_tables таблица Attempt с индексами
занимала 144 КБ, число мёртвых строк оценивалось в 2. Признаков существенного
разрастания таблицы по этим данным нет. Небольшим справочникам обычно достаточно
последовательного чтения целой таблицы.

Для первичного анализа использовались pg_stat_user_tables, pg_stat_user_indexes,
pg_constraint, pg_index и pg_total_relation_size. Из 24 внешних ключей на момент
обследования 19 не имели на ссылающейся стороне индекса с подходящим первым
столбцом. Для оптимизации выбраны поля, участвующие в замеренной нагрузке.

2. Методика

Тестовая копия perf_check содержит 7 900 студентов, 7 800 записей о членстве
в группах и 107 700 оценок. Студенты и оценки размножены из исходного набора.
Число групп, преподавателей и аттестаций оставлено исходным. Копия нужна,
чтобы исследовать рост объёма оценок и размеров групп. На ней выполнялся
VACUUM ANALYZE.

Встроенная оценка выполнена через EXPLAIN (ANALYZE, BUFFERS). Для быстрых
запросов указана медиана шести замеров после одного прогревочного прогона.
Для исходного Q8 выполнены один прогревочный и один зачётный замер из-за
длительности запроса. Значения Execution Time отражают время работы сервера.
Операции сравнивались с одинаковыми параметрами, при прогретом кэше.

Q1–Q5 после изменений используют добавленные индексы. Например, в Q1
число обращений к страницам в shared buffers снизилось с 728 до 21.
В Q4 индекс используется для фильтра по группе, а выигрыш по времени меньше,
поскольку соединение по-прежнему читает таблицу студентов. Изменения времени
Q6 и Q7 невелики. Планировщик сохранил Seq Scan по Attempt, так как запросы
обрабатывают всю или почти всю таблицу.

В исходном Q8 связанный подзапрос рассчитывал среднее по группе 6 800 раз.
В новой версии оценки агрегируются по студентам один раз, затем оконные суммы
вычисляют среднее по группе с весом по числу оценок. Число обращений к страницам
в shared buffers снизилось с 5 202 786 до 823. На увеличенной копии обе версии
вернули по 3 533 строки, на рабочей базе по 34. EXCEPT ALL в обоих направлениях
показал 0 различий на каждом наборе.

4. Нагрузочное тестирование

Проверки выполнялись на той же копии в 4 клиентских соединениях. На каждый
сценарий приходилось по 250 операций на клиента, 1 000 на один прогон. Перед
каждой серией выполнялся VACUUM ANALYZE. В каждом зачётном прогоне 0 ошибок.

Встроенный pgbench 18.6, чтение. Одна операция состоит из четырёх SELECT:
оценки студента, оценки по аттестации, список группы, подсчёт оценок преподавателя
за месяц. Средняя задержка снизилась с 14,902 до 2,234 мс, пропускная способность
выросла с 268,42 до 1 790,12 операций в секунду.

Встроенный pgbench 18.6, запись. Одна операция — BEGIN, INSERT оценки с
проверками триггеров, ROLLBACK. Средняя задержка снизилась с 5,701 до 0,222 мс.
Это испытание измеряет работу INSERT и проверок без стоимости сохранения COMMIT.

Сторонний Locust 2.47.0 и драйвер Psycopg 3.3.9. Одна операция — те же четыре
SELECT с получением всех строк. До оптимизации медиана составила 15 мс,
95-й перцентиль 17 мс. После оптимизации медиана составила 3 мс, 95-й
перцентиль 3 мс. Показатели относятся к локальному запуску на искусственно
увеличенном наборе. Разные клиенты и разные параметры нагрузки могут дать
другие значения.

5. Внесённые изменения

Индексы B-tree:
  Attempt (StudentID, AssessmentID) — оценки студента и подсчёт попыток.
  Attempt (AssessmentID) — оценки для ведомости.
  Attempt (TeacherID, Date) — фильтр по преподавателю и диапазону дат.
  StudentGroup (GroupID) — получение состава группы.

На тестовой копии индексы заняли суммарно около 3,91 МиБ. Индексы ускоряют
проверенные запросы и требуют дополнительного места и обновлений при записи.

Рабочая база проиндексирована. Script.sql создаёт схему с индексами.
Lab14.sql содержит команды индексации и новую версию Q8. Исходный пример
связанного подзапроса сохранён в Lab11.sql для лабораторной №11.

Оптимизированный grsu_dump.sql восстановлен в чистую проверочную базу.
Совпали число студентов, число оценок, контрольная сумма всех строк Attempt,
список четырёх добавленных индексов и результат проверки эквивалентности Q8.

Вывод

Основные затраты возникали при поиске по оценкам и при повторном вычислении
среднего по группе. Индексы ускорили выборки и проверку попыток, а однократная
агрегация и оконные суммы устранили повторную обработку оценок в Q8. При
подготовке отчётов по всей таблице планировщик по-прежнему использует полный
просмотр, соответствующий объёму данных, требуемому этими запросами.
